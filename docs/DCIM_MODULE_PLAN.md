# DCIM module (devices, racks, interfaces, cables): plan

Status: **phases A to D built (see Status at the end); phase E skipped.** Source: the DCIM app of NetBox (`sampark_netbox/netbox/dcim`, Django). As with IPAM, NetBox is not copied: its rules are re-implemented here (FastAPI, SQLAlchemy, Alembic, Vue).
Branch: `feature/ot-lifecycle`. Database: schema `assets_lifecycle` (`DB_SCHEMA`). IPAM (prefixes, addresses, VLANs, VRFs) is already built and is not repeated.

## What is already here (reuse, do not rebuild)

| Requested | Already in this application | Gap |
|---|---|---|
| Device name, serial, asset tag, site, location/room | `assets`: `name`, `serial_number`, `tag`, `site_id`, `location_id`, `area_id` | none |
| Role (switch, gateway, firewall, non-iot-machine) | `asset_types` (Switch, Gateway, Firewall and Conventional Machine exist) | none: the asset type is the role |
| Device type (manufacturer + model) | `assets.manufacturer_id` + free-text `assets.model` (1,197 assets have a manufacturer, 1,246 a model) | no catalogue, so no rack height |
| Rack ID, rack unit (position, face) | nothing | **new** |
| Custom fields for non-IoT machines (voltage, amperage, kW, schematics, parent PLC) | per-type fields: `asset_types.fields_schema` (text, number, date, select, boolean) stored in `assets.custom_fields`; `asset_documents` | configuration, plus one column for the parent PLC (see C) |
| Interface name, MAC, IP, mask, gateway | `asset_interfaces` (768 rows, 685 with a MAC) | missing: port type list, enabled, MTU, PoE, speed |
| Cable between two ports | `asset_connections`: parent/child asset, type, `local_interface_id`, `remote_interface_id` (36 of 56 rows have both ends) | no status, label, colour, length; interface ends not enforced |
| Topology map | `NetworkMap.vue`, fed by the connections | does not show ports, racks or PoE |
| IP addresses, prefixes, VLANs, VRFs | IPAM module (done) | Purdue mapping (see D) |
| MAC to IP binding | interface MAC plus the IPAM address assigned to that interface | no single view |

## Approach (same as IPAM)

- **Additive.** New tables, columns (nullable), routes, pages and one permission section `dcim` (read 1, write 2, delete 3; import and bulk need 4). No existing screen changes meaning.
- Tenant on every row, audit log on every change, paged lists (`{total, skip, limit, has_more, items}`), pure rules in a service module, English and Italian text, `use_alter` where a foreign key closes a cycle.
- **Speed from day one.** Lists are paged on the server and resolve related names in one query per type, never one per row (the lesson of the dashboard and audit log fixes).
- **Real data only.** Device types are backfilled from the real manufacturer + model pairs. Racks, rack positions and cable lengths are **not in the current data**, so they are entered or imported, never invented.
- **NetBox concepts left out:** tags, contacts, change-log, regions, site groups, virtual chassis, modules and module bays, console/power/cooling ports, front/rear ports (patch panels), device bays, inventory items, cable bundles. Each can be added later.

## Phases

### A. Racks and device types
- **Tables:** `dcim_racks` (name, site, location, `u_height`, `width`, `starting_unit`, `desc_units`, `facility_id`, `serial`, `asset_tag`, `status`, `airflow`, `role_id`, comments), `dcim_rack_roles`, `dcim_device_types` (manufacturer, model, `u_height`, `is_full_depth`, `airflow`, `part_number`, comments; unique per tenant on manufacturer + model).
- **Asset columns (nullable):** `device_type_id`, `rack_id`, `rack_position` (decimal, in U), `rack_face` (front, rear), `airflow`.
- **Rules:** a device fits inside the rack height; two devices cannot take the same unit on the same face unless one is half depth; position needs a rack; a rack must belong to the asset's site.
- **Backfill:** one device type per distinct (manufacturer, model) of the existing assets, then link the assets. Height starts empty (unknown), set later or by CSV.
- **API:** `/dcim/racks`, `/dcim/rack-roles`, `/dcim/device-types` (CRUD, paged, CSV import and export), `/dcim/racks/{id}/elevation` (units with the device in each), `PUT /assets/{id}/rack-position`.
- **UI:** Racks list and detail with a front/rear elevation, Device types list, a "Rack" block on the asset page (rack, U, face).

### B. Interface detail and cables (the physical topology)
- **`asset_interfaces` new columns:** `port_type` (NetBox type list: 1000base-t, 10gbase-x-sfpp, SFP, LC fibre ...; the existing free text `type` is mapped to it and kept), `enabled` (default true), `mtu`, `speed_kbps`, `duplex`, `mgmt_only`, `poe_mode` (pse or pd), `poe_type`, `poe_power_draw_w` (watts, added because PoE draw matters for cameras and sensors; not a NetBox field), `label`.
- **Cables:** extend `asset_connections` instead of a second cable table, because the network map, the dependency analyzer and the IEC 62443 conduits already read it. New columns: `cable_type` (cat5e, cat6, fibre ...), `status` (connected, planned, decommissioning), `label`, `color`, `length`, `length_unit`. Rules: an interface carries at most one cable; both ends must be interfaces of the two assets; the 20 rows with a missing end are listed in a "to complete" view, not deleted.
- **Trace:** `GET /dcim/interfaces/{id}/trace` returns the far end (switch port to PLC, camera or server NIC). One hop for now; patch panels would add hops later.
- **Topology:** `GET /dcim/topology?site=` returns nodes (asset, rack, location) and edges (cable with both port names, PoE, status). `NetworkMap.vue` reads it to show port labels, PoE and unconnected ports.
- **API / UI:** `/dcim/interfaces` (paged, filter by asset, type, enabled, PoE), `/dcim/cables` (list, create from two interfaces, bulk CSV: A device + port, B device + port), a "Cables" page and a PoE budget per switch (sum of the draw of its PoE ports).

### C. Non-IoT machine profile (mostly configuration)
- Add fields to the **Conventional Machine** asset type through `fields_schema`: Voltage (V), Amperage (A), Power rating (kW), Mechanical schematic (link), Electrical schematic (link). The 117 existing machines keep their data.
- **Parent PLC / controller:** `assets.parent_asset_id` already exists but means "this asset is a component inside another asset (a module in a PLC rack)", which is physical containment, not "controlled by". So add a dedicated nullable `controller_asset_id` (same site, asset type PLC or controller), shown on the machine page and as an incoming link on the PLC page. This is the one schema change in phase C (one nullable column, one migration).
- **Small gap:** `fields_schema` has no unit; units go in the field label.
- Schematic files stay in `asset_documents`; the link fields are for external URLs.

### D. IPAM glue
- **MAC to IP bindings:** a read-only view and CSV export joining interface MAC, IPAM address, VRF and asset (no new table). Duplicate MACs across assets are flagged. A `dcim_mac_addresses` table (several MACs per interface, NetBox style) only if you need more than one MAC per interface.
- **Purdue-level segmentation:** the Purdue level is already on assets and asset types. Options: (1) prefix roles named Purdue L0-L5 (no migration), or (2) a `purdue_level` column on VRFs and prefixes. The plan recommends (1) plus a report of assets whose address sits in a prefix of a different Purdue level. VRFs stay per site.

### E. Optional: one-time import from a NetBox server
- A command or page that reads the NetBox REST API (`/api/dcim/devices/`, `/cables/`, `/interfaces/`, `/api/ipam/...`) with a read-only token and fills racks, device types, cables and interface details, matching assets by serial or name. Dry run first, like the IPAM imports. Only if a running NetBox has data you want to bring over.

## Order, size, tests

| Order | Phase | Migration | Size |
|---|---|---|---|
| 1 | C: non-IoT profile | 1 (one column) | small |
| 2 | A: racks and device types | 1 (3 tables, 5 columns) | large |
| 3 | B: interfaces and cables | 1 (columns only) | large |
| 4 | D: MACs (several per interface) and IPAM glue | 1 (one table, backfilled from the interface MAC) | medium |
| - | E: NetBox import | skipped | - |

Each phase ends with backend tests (rules, tenant scope, paging, query count), a PostgreSQL smoke run, a migration check on a throwaway database (upgrade, downgrade, backfill), a frontend build, English/Italian locale parity, and a short status note here. Nothing is committed until you say so.

## Decisions (answered)

1. **Cables:** extend `asset_connections` (no separate cable table).
2. **Racks data:** a CSV from you. Phase A therefore includes a CSV import for racks and for rack positions of devices (dry run first, like the IPAM imports).
3. **Purdue:** prefix roles named Purdue L0-L5 (chosen by the plan, no migration), plus a report of assets whose address sits in a prefix of another level.
4. **MAC:** same as NetBox: several MAC addresses per interface, each its own row (`dcim_mac_addresses`), with one marked as the interface primary MAC. Phase D grows from "a view" to a table, a migration from the existing single MAC column, and a CSV.
5. **NetBox import (phase E):** skipped for now.
